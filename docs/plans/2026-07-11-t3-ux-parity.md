# T3-Code UX Parity Implementation Plan

> **For agentic workers:** This plan is executed by an orchestrated implementation workflow
> (sequential task agents in the `wizard/t3-ux` worktree, battery-verified between waves).
> Steps use checkbox (`- [ ]`) syntax for tracking. Every task = one commit. Research record:
> `docs/plans/2026-07-11-t3-ux-parity-analysis.md`.

**Goal:** Bring terminal.viktorbarzin.me to T3-Code-level UX — real fonts, themed ANSI palettes,
contrast, notifications, session UX, polish, PWA install, flow control — while remaining a true
terminal emulator that renders Claude Code's TUI (workflows, spinners, sixel) flawlessly.

**Architecture:** All frontend work lands in the single-file `frontend/index.html` (no build
step; served by patched ttyd). Server-side additions extend the two existing Go services
(tmux-api, clipboard-upload) and the existing local ttyd patch. Infra changes (PWA asset
carve-out) land in `infra/stacks/terminal/main.tf` via Terraform/CI. A committed dev harness
(`scripts/devserve/`) reproduces the production routing locally so every task is verified with
a real browser (Playwright) against real ttyd+tmux before anything deploys.

**Tech stack:** xterm.js 5.5.0 (pinned; 6.0 deferred), ttyd 1.7.7 + local patch, tmux 3.4,
Go 1.21 services, vanilla JS/CSS, JetBrains Mono + Iosevka-subset webfonts, Terraform.

### Verdict: MIRROR (evidence-decided)

- The state-based differ passed **16/16 CDP-synthesized IME scenarios**
  (composition growth and replacement-at-commit, autocorrect swaps,
  suggestion taps, select-all overwrite, dictation bursts) and converged

  Code's own composer — including mid-string edit convergence inside

  (xterm #2403/#3600/#675) is an EVENT-interpretation failure and the
  mirror is event-shape-agnostic **by construction** — it diffs

  post-mutation — so that class cannot reach it.
- Zero double-sends are possible by construction: an unchanged value
  diffs to nothing. Every red result across the three implementation
  test rounds was a test-harness bug, never the differ model.
- The one genuine gap found — receivers disagree on the delete unit —
  is closed by a measured, receiver-agnostic three-branch rule keyed on
  the verified DEL-past-empty no-op (record below).

### Six v1 constraints (verbatim — do not re-litigate without new evidence)

1. no pty cursor tracking or arrow repositioning (mid-string =

   complaint)
2. composition streams through
3. Enter always submits (multiline = bracketed paste or
   backslash-continuation)
4. the field never contains \n
5. desktop/fine pointers zero change

### Divergence contract (verbatim)

**"the field owns only bytes it streamed since its last reset; any
out-of-band byte resets it"** — Enter and every soft key hand the line
back to the TUI. Reset-site census on the shipped branch: the

### Measured delete-unit record (receivers and probes named)

- **Claude Code's composer deletes one GRAPHEME per 0x7f** — probed by
  streaming a multi-codepoint emoji (U+1F44D U+1F3FD, 👍🏽) into Claude
  Code's own input box through the real ws→ttyd→tmux stack: one DEL
  removed the whole grapheme.

  editing) delete one CODEPOINT per 0x7f** — same probe: one DEL removed
  only the U+1F3FD modifier; the post-submit echo proved exact
  codepoint-level removal.
- **DEL past empty is a verified no-op on BOTH receiver classes**
  (over-deleting from a known-empty line produced zero side effects) —
  this is what makes the NUKE branch receiver-agnostic.
- The three-branch rule in `reconcile()`: (1) nothing deleted → stream
  the insertion; (2) deletion counts agree in graphemes and codepoints
  (plain text) → one DEL per unit + tail retype; (3) counts disagree
  (emoji/ZWJ/combining) → DEL × codepoints(lastValue) — at least the
  receiver's own unit count, the excess absorbed by the no-op — then
  retype the whole line.

## Addendum 9 — IPv6 PMTU blackhole fixed at the router (2026-07-13, deployed as 92c6cdd)

Root cause of the Addendum-5 Apple-push blackhole, found and fixed at the site level on Viktor's
go-ahead. The house's IPv6 is an HE tunnelbroker gif on pfSense with MTU 1280 (deliberate), but
LAN radvd advertised AdvLinkMTU 1500 — every LAN host believed a 1500-byte path and depended on
PMTUD, and Apple's load balancers drop ICMPv6 Packet-Too-Big (ECMP), so their 1440-byte TLS
segments blackholed after the handshake. The kernel's PTB cache (mtu_expires=600s) made it
"work for 10 minutes" after any successful PTB, then re-break. Fix: pfSense Interfaces →
HE_IPv6 (gif0) MSS 1280 → `scrub on gif0 inet6 all max-mss 1220` (v4 1240) — applied via filter
reload, no interface bounce; config revision + on-box backup kept. Proof: fresh-cache curl -6 to
web.push.apple.com answers 405 in 0.54 s (was an 8 s timeout), packet capture shows Apple's
SYN-ACK arriving with the clamped mss 1220, and POST /push/test delivered 3×201 over IPv6. The
tcp4-forcing dialer in tmux-api's push client was then removed per its own removal note (tests
re-pinned to assert dual-stack dialing) — Web Push now doubles as a daily canary of the site v6
path. Diagnostic pattern recorded: "v6 connects then stalls to ONE provider" = PMTU blackhole;
A/B with `ip -6 route replace <prefix> mtu 1280` proves it in seconds.

## Addendum 16 — kinetic scroll v2: deterministic rows + real momentum (2026-07-14, deployed as a79ce72)

Viktor's on-device verdict on Addendum 15: "still somewhat clunky. not fast enough, the scroll
then release doesn't continue the movement — can we make it feel like a native scroll?" Both
v1 defects were then MEASURED, not guessed: (1) xterm 6 damps sub-50px pixel-mode wheel deltas
to ×0.3 — a finger's ordinary 5–15px per-frame moves lose 70% of their motion at ANY
multiplier (10 × dy=−5 wheels → 0 app events), and mouse-tracking panes get at most ONE app
event per DOM wheel event; (2) v1's momentum gate (two-sample velocity + a binary 80ms
pause-then-lift rule) ate genuine flicks. v2 replaces emission: feedScroll() accumulates
finger px and dispatches DISCRETE one-row DOM_DELTA_LINE wheels (undamped, one-row-exact,
k per frame with a burst cap) — deterministic finger→content, speed = rows per finger
row-height, IDENTICAL in copy-mode and Claude-Code-class panes (measured 0.98/1.47/1.96/2.99
at 1/1.5/2/3×). Momentum: ring-buffer release velocity (100ms window) drives the SAME emitter
under exponential decay τ=325ms (UIScrollView-normal feel), floor 0.5 row/s, cap 4 screens.
The stationary-lift problem got a principled fix: browsers DEDUPE identical-coordinate
touchmoves (a held finger produces NO samples), so the gate is the MIN of event-time and
handler-time gap between newest sample and touchend — ≤180ms only attenuates (exp(−gap/400):
delivery latency trims a flick, never kills it), >180ms = held still → no coast. Flicks with
0ms AND 120ms lift gaps coast (the defect-1 regression guard); a 250ms hold and a slow
decelerating drag never coast. Any pty-bound byte cancels the coast at the sendInput choke
point (belt: touchstart/trusted-wheel/soft-key/reattach cancels). Pref RE-KEYED per the
burned-key discipline: gestures.scrollSpeed retired, gestures.scrollSpeedV2 ∈ 1/1.5/2/3
DEFAULT 1× = true native one-to-one (≈3× v1's effective Claude-Code rate); scrollMomentum
keeps its key. Verification: the agent's implementation + my three finishing fixes
(sendInput-choke cancel, min-clock stationary gap, event-timestamp samples) took the driver
from 3 failing legs to 100% green — determinism both pane classes, momentum incl. gap flicks,
stop-contract cancels (zero events past mark+150ms), cap, precision, §A.5 + [M.6]. Two
harness gotchas recorded in BATTERY: the one-shot ghost-hint toast overlays the swipe path on
fresh profiles and SWALLOWS touches (pre-seed the marker), and the CDP pipeline can leak ≤3
same-frame stragglers around a cancel mark — assert the stop, not the frame. DEVICE-MANUAL:
1× drag ≈ one line per row-height; flicks MUST coast now and any touch/key stops them; slow
drags and still-holds never coast; the Settings dial (1–3×) and momentum toggle remain.
